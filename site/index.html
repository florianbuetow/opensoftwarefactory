A local software factory that runs on Kubernetes: agentic workflows, multi-agent teams, human gates, interactive refinement, and full tracing, evals, and cost observability in one UI.

GitHub Read more

Platform

A local Kubernetes (KIND) cluster of small, focused services managed through one justfile, with factory-ui as the single browser control room.

  • Core infrastructure: Kubernetes (KIND), temporal, jetstream, blobstore, openobserve, and telemetry-collector.
  • Execution & UI: factory-ui, orchestrator, agent, evaluation, and devpod.
  • Registries, gateways & repos: agent-registry, policy-registry, skill-registry, llm-gateway, mcp-gateway, tool-gateway, connectors, and git-host.

Agentic workflows

The workflow is the source of truth. Temporal executes configurable graphs of pinned agents, teams, interactive sessions, and gates, triggered manually or deterministically through event intake.

  • Every step pins the exact agent, policy, and skill version it runs, with fail-fast execution and no fallbacks.
  • Intake: Event bindings hash the event, binding, and pinned workflow version into one idempotent run ID.
  • Re-run any past workflow with its original input and versions to reproduce a baseline or compare changes.

Teams of agents

Coordinate multiple agents inside a single workflow step with a designated lead, direct inter-agent comms, and a shared workspace.

  • Agents exchange messages via direct inter-agent comms whose full logs are stored in the blobstore.
  • Members collaborate on shared workspace files and emit a structured manifest as the step's output.
  • Inspect live or finished inter-agent comms and workspace files directly from Runs and Decisions.

Human in the Loop

A person is a first-class step in any workflow - whether reviewing and gating work before it moves forward or refining artifacts interactively with agents.

  • Human review gates: Pause a workflow until someone approves or rejects on Decisions; rejections can stop the run or route back to an earlier step, and repository publishes can require approval first.
  • Interactive refinements: Pause a run in a session where a person and one or more pinned agents iterate together on shared files before continuing.
  • Every human decision and session record is stored as an artifact on the run's trace.

Agent Registry

Saving an agent never overwrites. Every edit writes the next immutable version beside the old one, and every run keeps its own prompt evidence.

  • Each agent version pins its system prompt, model settings, and attached tools.
  • Workflow steps pin an exact agent version, so older runs continue loading the version they used.
  • Each attempt copies its source and compiled prompts to runs/<trace>/_evidence/; missing evidence is reported honestly.

Agent Toolbox

Equip agents with versioned skills, tightly governed MCP tools, and built-in tools.

  • Skills: Versioned SKILL.md instructions and scripts unpacked and run in the dev pod against /workspace.
  • MCP & tools: External MCP servers sit behind mcp-gateway with explicit allowlists and denylists; built-in tools run via tool-gateway.
  • A tool call is refused unless explicitly allowed; the gateway never registers servers by itself.

Connectors

Connect workflows to Git repositories and isolated dev pods where agents write, test, and propose code changes.

  • Git repositories: Connect GitHub or plain Git repositories, or use the bundled local git-host for experiments.
  • Dev pods: Spin up sandboxed clones on dedicated work branches so agents can edit files and run commands safely.
  • Access & approvals: Control read/write credentials per repository and require human approval before publishing changes.

Context

Manage the versioned policies, skills, and stored artifacts that shape how agents behave and what they can read and produce.

  • Policies: Versioned rules stored in policy-registry and copied into each run's evidence folder when applied.
  • Skills: Versioned skill folders in skill-registry carrying instructions and scripts.
  • Artifacts: Inspect every stored blob in blobstore with its creator and trace ID.

Tracing, evals & observability

Every run leaves one trace of blobs under runs/<trace>/. Judges run as ordinary scoring workflows, provider token usage stays immutable while costs recalculate from current prices, and OpenObserve captures logs, metrics, and traces.

  • The trace ID is the Temporal workflow ID; every artifact carries its creator and trace ID, including nested workflows.
  • Judges write JSON artifacts mapped to named metrics - fix a mapping and re-extract without another model call.
  • Update a model price or EUR/USD rate to recalculate costs cleanly without altering usage records or double-charging.

Run it on your machine

Needs Colima, the Docker CLI, KIND, kubectl, just, Node.js 24+, Go 1.26+, uv, and an OpenAI-compatible LLM API such as LM Studio or Ollama.

git clone https://github.com/florianbuetow/opensoftwarefactory.git
cd opensoftwarefactory
claude "Configure the LLM gateway to use my OpenAI-compatible LLM API, then run just start and fix any issues you encounter"
  • just start brings the factory up from any state
  • just info shows each service's address and status
  • just status shows pods and services
  • just help lists every command

How to get unstuck

Most of the factory is driven by configuration, so this page does not walk through every setting. When something does not work, ask the AI coding agent in your terminal to read the repository and fix it. It will find the right file faster than any guide.

claude "just start fails, find out why and fix it"
codex  "just start fails, find out why and fix it"
grok   "just start fails, find out why and fix it"
agy -i "just start fails, find out why and fix it"

Limitations

The factory is not meant to scale to production environments.

  • It is an educational tool with no production hardening.
  • It is built to run on a single-node KIND cluster on your workstation.

How to contribute

We don't accept code changes. We accept natural-language requests for changes that specify behaviors, functionality, and features.

  • Describe the behavior, functionality, or feature you want - a request may include implementation suggestions.
  • The repository maintainers make all code changes after reviewing your request.
